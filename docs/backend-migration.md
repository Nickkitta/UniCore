# Переход UniCore с Supabase на собственный сервер

## Цель и контекст

Сейчас весь бэкенд UniCore — это Supabase:

- вход и регистрация — Supabase Auth;
- бизнес-логика — PL/pgSQL-функции с `auth.uid()` и правила доступа RLS в [supabase/migrations/](../supabase/migrations/);
- фотографии — Supabase Storage.

Цель — свой сервер на TypeScript в этом же репозитории, который поднимается на своём хостинге. Приложение работает с ним через тот же интерфейс [`CampusRepository`](../src/services/contracts.ts), поэтому экраны почти не меняются.

**Прод-версии и настоящих пользователей нет.** Данные из Supabase не переносим и переходный период не нужен: новая база наполняется сидером. Supabase остаётся рабочим до этапа 9, чтобы было с чем сравнивать.

## Решения и стек

| Решение               | Что выбрано                                                                           | Почему                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Структура репозитория | Монорепозиторий на npm workspaces: `apps/mobile`, `apps/api`, `packages/shared`       | Общие типы и валидация, клиент и сервер меняются одним коммитом                          |
| Бизнес-логика         | Переписывается на TypeScript в сервисном слое сервера; PL/pgSQL не переносим          | Обычный бэкенд, проще отлаживать и расширять (push, чат через WebSocket, админка)        |
| Авторизация           | Своя: argon2id, короткий JWT доступа и ротируемый refresh-токен в базе                | Полный контроль без внешних сервисов                                                     |
| Данные                | Без переноса, база наполняется сидером                                                | Настоящих пользователей нет                                                              |
| Сервер                | Node.js 22, TypeScript, Fastify, zod                                                  | Зрелый фреймворк, схемы zod общие для клиента и сервера через `packages/shared`          |
| База                  | PostgreSQL, Drizzle ORM и миграции drizzle-kit                                        | Типизированные запросы, транзакции и `SELECT … FOR UPDATE`, тот же код работает с PGlite |
| База для разработки   | PGlite в файле, если не задан `DATABASE_URL`; Postgres из docker compose — по желанию | Разработка на Windows без Docker; Postgres нужен для проверки конкурентности             |
| Токены и пароли       | `jose` для JWT, `@node-rs/argon2` для паролей                                         | Готовые сборки под Windows и Linux, без node-gyp                                         |
| Почта                 | nodemailer: в консоль при разработке, SMTP в проде                                    | Ссылки подтверждения видны в терминале, без почтового сервиса                            |
| Фотографии            | Файлы на диске сервера, выдача через API по ссылкам с HMAC-подписью                   | Не нужен отдельный S3; ссылки работают в `<Image>` и на web, и на телефоне               |
| Защита и логи         | `@fastify/rate-limit`, pino с маскировкой токенов и паролей                           | Лимиты на вход раньше давал Supabase                                                     |
| Тесты                 | vitest на PGlite; тест конкурентности на настоящем Postgres                           | PGlite уже используется в проекте, тесты идут без Docker                                 |
| Обновление данных     | Опрос раз в 15 секунд, как сейчас                                                     | WebSocket в объём перехода не входит                                                     |

Таблицы в новой базе — без префикса `unicore_`: база больше не общая с другими приложениями.

## Контракт API

Все адреса с префиксом `/v1`. Защищённые запросы идут с заголовком `Authorization: Bearer <access token>`. После изменяющих запросов клиент, как и сейчас, заново загружает `GET /v1/snapshot`.

| Метод `CampusRepository`    | HTTP                                                                              | Ответ                                       |
| --------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------- |
| `load`                      | `GET /v1/snapshot`                                                                | `Snapshot` того же вида, что сейчас         |
| `signIn`                    | `POST /v1/auth/sign-in` `{ email, password, portal }`                             | `{ accessToken, refreshToken, expiresIn }`  |
| `signUp`                    | `POST /v1/auth/sign-up` `{ email, password, name, partner? }`                     | токены или `{ verificationRequired: true }` |
| `resendConfirmation`        | `POST /v1/auth/resend-verification` `{ email }`                                   | 204                                         |
| `signOut`                   | `POST /v1/auth/sign-out` `{ refreshToken }`                                       | 204                                         |
| — (обновление сессии)       | `POST /v1/auth/refresh` `{ refreshToken }`                                        | новые токены                                |
| — (ссылка из письма)        | `GET /v1/auth/verify?token=…`                                                     | HTML-страница «Почта подтверждена»          |
| `updateProfile`, `setTheme` | `PATCH /v1/profile`                                                               | 204                                         |
| `toggleSaved`               | `PUT /v1/activities/:id/saved` `{ saved }`                                        | 204                                         |
| `toggleJoined`              | `PUT /v1/activities/:id/membership` `{ joined }`                                  | 204                                         |
| `createInvite`              | `POST /v1/photos` для каждого фото, затем `POST /v1/activities` `{ …, photoIds }` | `{ id }`                                    |
| `room`                      | `GET /v1/activities/:id/room`                                                     | `EventRoom`                                 |
| `postMessage`               | `POST /v1/activities/:id/messages` `{ body }`                                     | 204                                         |
| `setCohost`                 | `PUT /v1/activities/:id/members/:userId/cohost` `{ enabled }`                     | 204                                         |
| `removeMember`              | `DELETE /v1/activities/:id/members/:userId`                                       | 204                                         |
| `issuePartnerCode`          | `POST /v1/admin/partner-codes`                                                    | `{ code }`                                  |
| `reset`                     | нет, только режим mock                                                            | —                                           |
| `checkConnection`           | `GET /v1/health`                                                                  | `{ ok: true }`                              |
| — (фото в ленте)            | `GET /v1/files/:id?exp=…&sig=…`                                                   | `image/jpeg`                                |

**Формат ошибки:** `{ "error": { "code": "UNICORE_FULL", "message": "…" } }`. Текст для пользователя клиент берёт по коду из общей таблицы в `packages/shared`; `message` нужен для отладки.

| HTTP | Коды                                                                                                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 401  | `UNICORE_AUTH_REQUIRED`, `UNICORE_INVALID_CREDENTIALS`                                                                                                       |
| 403  | `UNICORE_ROOM_DENIED`, `UNICORE_ORGANIZATION_FORBIDDEN`, `UNICORE_FORBIDDEN`, `UNICORE_EMAIL_NOT_CONFIRMED`, `UNICORE_WRONG_PORTAL`, `UNICORE_BAD_SIGNATURE` |
| 404  | `UNICORE_NOT_FOUND`                                                                                                                                          |
| 409  | `UNICORE_FULL`, `UNICORE_PAST`, `UNICORE_HOST`, `UNICORE_PARTNER_JOIN`, `UNICORE_EMAIL_TAKEN`                                                                |
| 413  | `UNICORE_FILE_TOO_LARGE`                                                                                                                                     |
| 422  | `UNICORE_INVALID_INPUT`, `UNICORE_INVALID_GROUP`, `UNICORE_INVALID_TAGS`, `UNICORE_INVALID_PHOTOS`, `UNICORE_INVALID_CODE`, `UNICORE_WEAK_PASSWORD`          |
| 429  | `UNICORE_RATE_LIMIT`                                                                                                                                         |

Коды бизнес-логики совпадают с теми, что сейчас бросают SQL-функции и разбирает `backendError` в [supabaseRepository.ts](../src/services/supabaseRepository.ts). Коды входа заменяют коды Supabase Auth (`invalid_credentials`, `email_not_confirmed` и т. п.).

## Этап 3. Авторизация

**Статус:** не начат · **Зависит от:** 2 · **Результат:** регистрация, вход, сессии и подтверждение почты работают без Supabase.

- [ ] 3.1 Пользователи и пароли:
  - пароли хешируются argon2id, почта приводится к нижнему регистру без пробелов;
  - пароль от 8 символов, имя от 1 до 40;
  - профиль студента создаётся в той же транзакции, что и пользователь.
  - Проверка: тесты — в базе нет пароля в открытом виде; `Test@Example.com ` и `test@example.com` — один аккаунт; короткий пароль даёт 422 `UNICORE_WEAK_PASSWORD`; повторная почта даёт 409 `UNICORE_EMAIL_TAKEN`.
- [ ] 3.2 Токены:
  - JWT доступа на 15 минут (`sub` = id пользователя);
  - refresh-токен — 32 случайных байта, в базе хранится только sha256, срок 30 дней;
  - при каждом обновлении выдаётся новый, а старый помечается использованным;
  - повторное предъявление использованного токена отзывает всю цепочку этой сессии.
  - Проверка: тесты — обновление выдаёт новую пару; старый refresh-токен после обновления даёт 401 и отзывает новый; токен доступа с истёкшим сроком или чужой подписью даёт 401.
- [ ] 3.3 Адреса `sign-up`, `sign-in`, `refresh`, `sign-out`. Портал (`student` / `partner`) проверяется на сервере: при несовпадении токены не выдаются.
  - Проверка: тесты — неверный пароль и несуществующая почта дают одинаковый ответ 401 `UNICORE_INVALID_CREDENTIALS`; студент через портал партнёра получает 403 `UNICORE_WRONG_PORTAL` без токенов; после `sign-out` refresh-токен не работает.
- [ ] 3.4 Подтверждение почты:
  - одноразовая ссылка на 24 часа, в базе хранится хеш;
  - `GET /v1/auth/verify` отдаёт HTML-страницу;
  - `resend-verification` не чаще раза в минуту и не раскрывает, есть ли такой аккаунт;
  - флаг `AUTH_REQUIRE_EMAIL_VERIFICATION` (по умолчанию `false` для закрытых тестов);
  - транспорт почты: `console` или `smtp`.
  - Проверка: тесты — при включённом флаге вход до подтверждения даёт 403 `UNICORE_EMAIL_NOT_CONFIRMED`; ссылка срабатывает один раз; просроченная ссылка показывает страницу с ошибкой. Вручную: регистрация через curl, ссылка из консоли открывается в браузере, после неё вход проходит.
- [ ] 3.5 Регистрация партнёра по промокоду в одной транзакции:
  - код ищется по sha256 от `lower(trim(code))`, не использован, срок не истёк;
  - код помечается использованным;
  - создаётся аккаунт и профиль партнёра с компанией.
  - Проверка: тесты — верный код работает один раз; использованный, просроченный и выдуманный дают 422 `UNICORE_INVALID_CODE`, и аккаунт при этом не создаётся.
- [ ] 3.6 CLI-команды `npm -w apps/api run admin:grant -- <email>` и `admin:revoke`.

## Этап 4. Бизнес-логика

**Статус:** не начат · **Зависит от:** 3 · **Результат:** все правила, которые сейчас гарантирует база, работают в TypeScript-сервисах и покрыты тестами.

- [ ] 4.1 Профиль (`PATCH /v1/profile`):
  - имя 1–40; институт до 80; курс пустой или 1–6; группа до 20; описание до 300;
  - интересы только из списка категорий; тема `violet` / `forest` / `light`;

  - Проверка: тест на каждое ограничение; попытка передать `accountKind`, `isAdmin` или чужой id игнорируется или даёт 422.
- [ ] 4.2 Создание события (`POST /v1/activities`):
  - название 5–80, описание 15–1500, место 3–120 (после trim);
  - категория из списка, вместимость 2–100, цена 0–1 000 000;
  - координаты: обе пустые или обе в допустимых пределах;
  - до 4 разных тегов из `eventTags`;
  - дата в будущем; тип `event`;
  - от имени сообщества публикует только его владелец.
  - Проверка: тест на каждое ограничение; прошедшая дата даёт 409 `UNICORE_PAST`; чужое сообщество — 403 `UNICORE_ORGANIZATION_FORBIDDEN`; неверные теги — 422 `UNICORE_INVALID_TAGS`.
- [ ] 4.3 Партнёрские события:
  - создать может только аккаунт партнёра;
  - бейдж обязателен и один из: «Стажировка», «Экскурсия», «Мастер-класс», «Встреча с командой»;
  - сообщество не привязывается;
  - организатор-партнёр не занимает место.
  - Проверка: студент с бейджем получает 403; партнёр без бейджа — 422; у события партнёра с вместимостью 2 могут записаться два студента.
- [ ] 4.4 Запись и отмена (`PUT …/membership`):
  - событие существует и пользователь не исключён из него, иначе 404;
  - организатор не может записаться (`UNICORE_HOST`), партнёр тоже (`UNICORE_PARTNER_JOIN`);
  - повторная запись не создаёт дубль;
  - на начавшееся событие записаться нельзя (`UNICORE_PAST`);
  - занятые места = 1 за организатора-студента + участники; при заполнении — `UNICORE_FULL`;
  - отмена удаляет запись и роль помощника;
  - всё в транзакции с `SELECT … FOR UPDATE` по строке события.
  - Проверка: тесты на каждое правило; два одинаковых запроса подряд дают одну запись.
- [ ] 4.5 Закладки (`PUT …/saved`): событие существует и пользователь не исключён; повторный запрос безопасен; закладки видит только владелец.
  - Проверка: тесты; в снимке другого пользователя чужие закладки не появляются.
- [ ] 4.6 Снимок (`GET /v1/snapshot`):
  - свой профиль с email и `isAdmin`; справочник групп; только свои сообщества;
  - все события, кроме тех, откуда пользователь исключён, — сначала новые;
  - `hostInfo` вида «ИМИТ · 4 курс»;
  - `attendees` = место организатора (0 для партнёра) + участники без текущего пользователя;
  - для партнёра: `organizationName` = компания, `partnerBadge` (по умолчанию «Партнёрская встреча»), `companyAbout`;

  - Проверка: тест сравнивает снимок с ожидаемым на подготовленных данных; тест на приватность — в ответе нет чужих email, описаний, интересов и списков участия.
- [ ] 4.7 Комната события (`GET …/room`, `POST …/messages`):
